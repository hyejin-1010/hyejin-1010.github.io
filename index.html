왜 전환했고, 무엇을 지켰나

전환 판단. 외주로 시작돼 누적된 기술 부채, 프론트 2명이 Dart·TS 두 언어를 병행하는 부담, 두 앱이 레포로 분리돼 생기는 이중 유지보수 — 이 셋을 근거로 수정 비용이 재구축 비용을 넘었다고 판단해 RN 전환을 제안했다. RN을 고른 핵심은 웹 개발자가 별도 언어 없이 앱을 유지보수할 수 있다는 점. 스타일도 웹과 같은 Tailwind 체계(NativeWind)로 통일했다.

지킨 것. 사용자가 앱이 바뀐 걸 인지하지 못해야 한다는 전제로, 기존 기능·UX를 1:1 재현하는 데 초기 설계·검증 시간을 집중 투자했다.

OTA 리스크 관리. 잘못된 업데이트가 전체 사용자에게 즉시 적용되는 위험이 있어, 도구 선정 단계에서 롤백 지원을 필수 기준으로 두고 Hot Updater를 선택·복구 절차를 검증했다.

문제 해결 사례. 특정일 크래시 22건 급증 → 대량 푸시 발송 시 메인 스레드 과부하로 원인을 규명하고 수신 핸들러 비동기화로 대응.

사람은 판단에만. 크래시 수집 → 이슈 등록 → 코드 작업 → PR 생성 → 배포 상태 전이까지 자동으로 돌되, 리뷰·머지라는 판단 지점은 반드시 사람이 잡는다. AI가 만든 결과물은 게이트(리뷰, 렌더 검증)를 통과해야만 반영된다.

자동화를 감시하는 자동화. 가장 위험한 건 조용히 멈추는 것 — 파이프라인 실패·봇 연결 끊김·수집 키 오염·토큰 만료를 각각 감시하는 워치독 4종을 두고, 감지 시 경보 또는 자동 복구한다.

문서 생성. 회사별 양식이 제각각인 계약서류를 엑셀 한 장으로 받아 커스텀 컴포넌트를 생성한다. 병렬 생성은 격리 워크스페이스로 충돌을 막고, PDF·xlsx 산출물이 기준 크기를 넘지 못하면 커밋 자체를 차단한다.

Vue 3TypeScriptViteTailwindPrimeVue
설계 결정과 교훈

TS 도입 설득. 착수 시점(2023.10) 회사 프론트는 전부 JS였다. 수십 메뉴·복잡한 폼·권한이 얽힌 어드민은 시간이 갈수록 리팩토링 비용이 커질 것으로 보고 TS를 제안, 팀 동의를 얻어 셋업했다. 런타임에서 발견되던 undefined 참조가 개발 단계에서 잡히기 시작했고, 이후 신규 프로젝트가 TS를 기본 채택했다.

추상화는 규모에 따라 재판단. 모든 입력 타입을 담던 단일 CustomInput이 타입 30개를 넘기며 1,000줄을 초과하고 readonly/disabled 개념이 섞였다. 2025.06 두 개념을 분리했고, 이후 본체를 키우는 대신 분리 가능한 타입을 독립 컴포넌트로 추출하는 방향으로 전환했다.

성능은 공통 레이어에서. 전 목록 화면의 기반인 useList에 500ms debounce를 한 번 넣어 중복 호출을 전역에서 제거 — 공통 추상화가 유지보수에 실제로 기여한 사례.
